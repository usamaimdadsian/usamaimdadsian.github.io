e:T1438,<h2>Node.js + Express.js Authentication API Boilerplate</h2><p>This is a project meant to be used as a starting point for APIs that require user authentication (registration and sign on). Sign on sessions are showcased with protected routes that pass through authentication middleware. API is designed to be consumed by a SPA.</p><p><strong>This is a WIP</strong>, if you find any issues or concerns with the security of the implementation, please, open a new issue or contact me directly <a href="https://twitter.com/yanglorenzana" target="_blank" rel="noopener noreferrer">@yanglorenzana</a> on Twitter.</p><blockquote><p>Read the <a href="https://www.ylorenzana.rocks/nodejs-api-authentication-tutorial-pt-1/" target="_blank" rel="noopener noreferrer">tutorial series</a> for this project if you&#39;d like a more detailed explanation and walkthrough.</p></blockquote><h4>WIP:</h4><ul><li>Password reset mechanism</li><li>Account lockout after too many unsuccessful login attempts</li><li>~~Another security mechanism against CSRF~~ :heavy_check_mark:</li></ul><h4>TODO:</h4><ul><li>Request throttling</li></ul><p>Tried following <a href="http://jsonapi.org/" target="_blank" rel="noopener noreferrer">json:api</a> specification for the design of the API for the error responses, but didn&#39;t get a good example for other response objects.</p><p>Project uses <a href="http://mongoosejs.com/" target="_blank" rel="noopener noreferrer">mongoose</a> for data modeling and <a href="https://expressjs.com/" target="_blank" rel="noopener noreferrer">express.js</a> for easy server setup.</p><p>The auth system uses 16 random bytes generated with the <a href="https://nodejs.org/api/crypto.html#crypto_crypto_randombytes_size_callback" target="_blank" rel="noopener noreferrer">node.js crypto module</a> as authentication tokens.</p><h3>Project Setup</h3><p>To run project locally:</p><ul><li>Clone repo</li><li><code>npm install</code> in root directory</li><li>Add your mongoDB uri to <code>secrets.js</code> file or add it to your ENV variables</li><li><code>npm start</code> to run nodemon in watch mode</li><li>Use <a href="https://https://www.getpostman.com/" target="_blank" rel="noopener noreferrer">postman</a> to test endpoints or curl if you&#39;re cool</li></ul><h3>Overview of auth system:</h3><ol><li>User registers account. Password is hashed and salted with bcrypt and is stored in database</li><li>User enters credentials, server validates credentials. If valid, a random 16 byte token is generated and stored in database along with the user ID of the requesting user</li><li>Token is set in a cookie along with the server&#39;s response</li><li>Client includes cookie on subsequent requests.</li><li>Protected endpoints send request through authentication middleware, which checks token received in request to exist in database and have a status of &#39;valid&#39;. The endpoints that use the authentication in this project are the GET/DELETE api/users/me and PUT api/users/logout. Meant to serve as examples of how it would work</li><li>To logout, client would send request to api/users/logout with their auth token. If token exists and is valid, set session status as &#39;expired&#39;</li></ol><h4>CSRF Protection</h4><ol><li>Implemented CSRF-tokens for CSRF mitigation. Read more at &#39;Synchronizer (CSRF) Tokens&#39; section of [OWASP CSRF Prevention](&lt;https://www.owasp.org/index.php/Cross-Site_Request_Forgery_(CSRF)_Prevention_Cheat_Sheet#General_Recommendations_For_Automated_CSRF_Defense&gt;)</li><li>Added new key to session schema. Every session now includes csrfToken key.</li><li>Whenever a new user registers or existing user logs in, a new session is initialized. Sessions now require a csrfToken to be generated along with the original bearer token (using the same <code>generateToken()</code> method).</li><li>Once session is initalized, server sets bearer token in a token cookie, but also responds with the session&#39;s csrf-token in body.</li><li>This csrf-token <strong>must</strong> be attached to the headers of every request as <code>csrf-token: &#39;YOUR TOKEN HERE&#39;</code> that _would change/modify server-side state_. In this case, the <code>DELETE api/users/me</code> and <code>PUT api/users/logout</code> routes require a csrf token.</li><li>Protected routes use <code>csrfCheck</code> middleware. This middleware should be added to any route that would change state. The csrfCheck for the delete user route is somewhat redundant as it requires the user to provide credentials, but I included it to serve as example.</li></ol><p>An example of login route response and placing the csrf-token in headers:</p><p><a href="https://s33.postimg.cc/6723bdo8v/postman-example.png" target="_blank" rel="noopener noreferrer">![postman-example.png</a>](https://postimg.cc/image/wfd80r8cb/)</p><h3>License</h3><p><a href="https://github.com/ylorenzana/node-express-api-auth/blob/master/LICENSE" target="_blank" rel="noopener noreferrer">MIT</a></p><p>---</p><p>Feedback and PR&#39;s welcome.
